# Банк задач

Банк задач хранит переиспользуемые задания для технических интервью. Условие задачи общее,
а исполняемые данные принадлежат конкретному языковому варианту. Создание, просмотр скрытых
данных, редактирование и удаление доступны только пользователю с `isAdmin = true`.

## Модель данных

| Таблица                           | Что хранит                                                                                        |
| --------------------------------- | ------------------------------------------------------------------------------------------------- |
| `ProgrammingTask`                 | `slug`, название, описание, сложность, активность и необязательного автора                        |
| `ProgrammingTaskVariant`          | язык, стартовый код, Harness, эталонное решение, статус проверки, ошибку и необязательного автора |
| `ProgrammingTaskCase`             | скрытый input и expected output конкретного языкового варианта                                    |
| `ProgrammingTaskHarnessTemplate`  | редактируемый без деплоя стандартный Harness для языка                                            |
| `Session.programmingTaskSnapshot` | неизменяемую копию задачи, варианта и тестов на момент создания сессии                            |

Связи `ProgrammingTask → ProgrammingTaskVariant → ProgrammingTaskCase` имеют `onDelete: Cascade`.
Сессия ссылается на задачу через `onDelete: SetNull`, но её JSON snapshot остаётся после удаления
задачи и сохраняет воспроизводимость уже созданного интервью.

## Статусы варианта и видимость

```text
DRAFT → VERIFYING → VERIFIED
                  ↘ FAILED

FAILED → VERIFYING → VERIFIED / FAILED   (повторная проверка того же варианта)
```

- При создании вариант сразу записывается как `VERIFYING`, а отдельная BullMQ-очередь
  `programming-task-verifications` получает job с `variantId` и редакцией варианта. HTTP-запрос
  не ждёт Code Runner и сразу возвращает `VERIFYING`.
- Worker очереди проверяет только один языковой вариант. Его тест-кейсы запускаются
  последовательно и прекращаются после первого несовпадения. Очередь проверки задач отделена от
  `code-executions`, поэтому создание задач не блокирует очередь запусков кода в сессиях.
- Перед каждым административным тест-кейсом worker проверяет `waiting/active` jobs очереди
  `code-executions`. Пока в сессиях есть ожидающий или выполняющийся код, проверка задачи ждёт и
  не отправляет новый запрос в общий Coderunner. Уже начавшийся тест-кейс не прерывается.
- Совпали все результаты — `VERIFIED`, заполняется `verifiedAt`, ошибка очищается.
- Ошибка запуска или несовпадение результата — `FAILED`, причина сохраняется в
  `lastVerificationError`. Вариант не удаляется, чтобы его можно было исправить.
- Повторная проверка обновляет существующий `variantId`; новая запись при каждой попытке не
  создаётся.
- BullMQ повторяет stalled/неуспешную job. Дополнительно backend раз в минуту ищет варианты,
  которые остаются `VERIFYING` дольше пяти минут, и восстанавливает их job. Детерминированный
  `jobId` из `variantId + updatedAt` предотвращает дубли при нескольких backend-инстансах.
- В публичный банк и в выбор задачи для сессии попадают только активные задачи, у которых есть
  `VERIFIED`-вариант выбранного языка. `DRAFT`, `VERIFYING` и `FAILED` кандидатам не выдаются.
- Admin edit endpoint возвращает все варианты независимо от статуса, включая скрытые тесты и
  эталонное решение.

## Frontend-флоу

### Создание — `/[locale]/tasks/new`

1. Первый шаг: название, описание и сложность.
2. Второй шаг: стек, стартовый код, Harness, тест-кейсы с ожидаемыми результатами и эталонное
   решение. Dropdown показывает все поддерживаемые языки: сохранённые варианты отмечены зелёным
   статусом, текущая ошибка — красным, ещё не реализованные — серым. При выборе языка стандартный
   Harness загружается из БД.
3. `Далее` сначала валидирует поля, сохраняет вариант и ставит его проверку в очередь. Клиент
   короткими запросами отслеживает статус. Переход к следующему языку происходит только при
   `VERIFIED`; использованный язык остаётся в списке с зелёным статусом и больше не выбирается
   повторно.
4. Пока после текущего варианта остаётся хотя бы один неиспользованный язык, рядом доступна кнопка
   `Далее`. После предпоследнего языка остаётся только `Завершить`.
5. `Завершить` проверяет текущий вариант и при успехе возвращает пользователя в банк. Поэтому
   администратор может остановиться после любого количества языков и не обязан заполнять все.
6. При `FAILED` форма показывает причину и остаётся на текущем языке. Следующая отправка вызывает
   повторную проверку того же `variantId`, а не создаёт дубль.

### Редактирование — `/[locale]/tasks/:id/edit`

1. Первый шаг содержит общие поля. `Сохранить` вызывает `PATCH` без Code Runner; `Далее` только
   переключает шаг.
2. Второй шаг редактирует выбранный языковой вариант. `Сохранить и проверить` записывает общие и
   исполняемые поля, заменяет тест-кейсы и ставит проверку варианта в очередь.
3. Селектор стека показывает все поддерживаемые языки и статус каждого варианта. Клик по языку со
   статусом `не реализован` сразу открывает чистую форму новой реализации; отдельной кнопки `Далее`
   на втором шаге нет.
4. Тултипы стартового кода, Harness, тестов и эталонного решения доступны по hover и keyboard
   focus. Скрытые тесты и эталонное решение никогда не показываются кандидату.

### Удаление

На странице редактирования администратор нажимает `Удалить задачу` и подтверждает необратимое
действие. Backend удаляет задачу, варианты и тесты; после ответа клиент очищает кэш и возвращает
пользователя в банк. Существующие сессии продолжают работать по сохранённому snapshot.

## API

Все маршруты требуют JWT. Публичный `ProgrammingTasksController` содержит только получение
доступных задач. Остальные маршруты находятся в `ProgrammingTasksAdminController`, на который на
уровне класса установлены `JwtAuthGuard` и `AdminGuard`. Одинаковый URL-префикс контроллеров не
создаёт конфликтов: Nest сопоставляет полную комбинацию HTTP-метода и пути каждого handler.

```text
GET    /programming-tasks?language=JAVASCRIPT
       → активные задачи с VERIFIED-вариантом языка

POST   /programming-tasks                                      admin
       { title, description, difficulty, language, starterCode,
         harnessCode, referenceSolution, testCases[] }
       → { id, slug, variantId, status, verificationError }

POST   /programming-tasks/:taskId/variants                     admin
       { language, starterCode, harnessCode, referenceSolution, testCases[] }
       → добавляет новый язык и возвращает VERIFYING после постановки job;
         повтор языка → 409

GET    /programming-tasks/:id/edit                             admin
       → общие поля + все варианты + скрытые тесты

PATCH  /programming-tasks/:id                                  admin
       { expectedUpdatedAt, title, description, difficulty }
       → сохраняет общие поля без верификации; устаревшая версия → 409

PUT    /programming-tasks/:taskId/variants/:variantId          admin
       { language, starterCode, harnessCode, referenceSolution, testCases[] }
       → обновляет тот же вариант и возвращает VERIFYING после постановки job

DELETE /programming-tasks/:id                                  admin
       → 204; каскадно удаляет варианты и тесты

GET    /programming-tasks/harness-templates/:language          admin
       → { harnessCode }
```

`input` и `expectedOutput` тест-кейса — JSON-значения: объект, массив, строка, число, boolean или
`null`. Harness читает JSON из stdin, вызывает решение и печатает результат. Импорты, сигнатура
функции и способ вызова зависят от языка и задаются в стартовом коде/Harness.

## Текущие ограничения

- `FAILED`-задача не видна в обычном банке. После ошибки создания её можно исправить в той же
  открытой форме; отдельного admin-списка черновиков и упавших вариантов пока нет.
- В локальном Docker backend выполняет seed при старте. Удалённая сидовая задача будет создана
  снова после перезапуска контейнера; пользовательские задачи seed не восстанавливает.

## Проверки

```bash
pnpm --filter backend test
pnpm --filter backend build
pnpm --filter frontend test
pnpm --filter frontend build
```

Тесты фиксируют admin-only доступ, постановку проверки в отдельную очередь, успешный и неуспешный
результаты worker, защиту от устаревшей job, добавление языков без дублей, повторную проверку,
отдельное сохранение общих полей, удаление, фильтрацию по `VERIFIED` и соответствие frontend API
backend-маршрутам.
