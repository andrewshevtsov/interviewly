# Релизы

Релизы выпускает [semantic-release](https://semantic-release.gitbook.io) из GitHub Actions. Версия одна на весь монорепо (`vX.Y.Z`), приложения в `apps/*` отдельно не версионируются.

> Статус: модель согласована, конфиг `release.config.js` готов; workflow запуска `release.yml` добавлен, но ещё не проверен в GitHub. Деплой по-прежнему идёт из `dev` по push; перевод на теги и staging — отдельная задача после демо.

## Ветки

| Ветка         | Назначение                                                                       |
| ------------- | -------------------------------------------------------------------------------- |
| `dev`         | Интеграция. Сюда вливаются PR с фичами и фиксами                                 |
| `release/x.y` | Ответвление под релиз, режется от `dev`. Принимает только багфиксы и cherry-pick |
| `main`        | Всегда равна последнему релизу. Тег ставится здесь                               |

```
dev ──●──●──●──●──●──────●──▶
          \                 ▲ (hotfix вливается обратно)
release/1.2 ──●──●──┐
                    ▼
main ───────────────● v1.2.0
```

Порядок:

1. Когда набор изменений готов, от `dev` режется `release/x.y`.
2. В `release/x.y` попадают только исправления; новые фичи идут в `dev`.
3. `release/x.y` вливается в `main` → semantic-release считает версию, пишет `CHANGELOG.md`, ставит тег и создаёт GitHub Release.
4. Hotfix: ветка от `release/x.y` → PR в `release/x.y` → патч-релиз; затем изменение вливается обратно в `dev`.

## Как коммиты определяют версию

Формат коммитов остаётся прежним (`префикс-ветки: Заголовок` + строки с маркерами `[+] [-] [~] [!] [!!]`), см. `.husky/commit-msg`. Тип релиза определяется по префиксу ветки в заголовке и маркерам в теле:

| Условие                                                               | Версия             |
| --------------------------------------------------------------------- | ------------------ |
| Маркер `[!!]` в теле                                                  | major              |
| Префикс `feature/…`                                                   | minor              |
| Префикс `hotfix/…`, `bugfix/…` или только номер задачи (`BE-10_1: …`) | patch              |
| Префикс `infra/…`, `chore/…`, `docs/…`                                | релиз не создаётся |

Берётся максимальный уровень среди коммитов с прошлого релиза. Маркер `[!]` (важное, но не ломающее) на версию не влияет.

Правила реализованы в `release.config.js` и проверены dry-run на истории `dev`. Коммиты вида `Merge …` и без `префикс: ` в заголовке релиз не вызывают. В заметки релиза попадают только `feature`, `hotfix`, `bugfix` и номер задачи; `infra`, `chore` и `docs` видны, только если помечены `[!!]`.

Версия хранится только в git-теге: `package.json` не правится, `CHANGELOG.md` обновляется коммитом `release: vX.Y.Z [skip ci]`.

semantic-release настроен только на `main`; отдельные maintenance-ветки `release/*` подключим, когда понадобятся патчи к старой версии.

## Как выпустить релиз

Релиз запускается только вручную: Actions → Release → Run workflow, ветка `main` (`.github/workflows/release.yml`).

- Галка `dry_run` считает версию и заметки, не создавая тег, коммит и GitHub Release. Сначала запускайте с ней.
- Без галки workflow ставит тег `vX.Y.Z`, коммитит `CHANGELOG.md` в `main` и создаёт GitHub Release.
- Релиз не создаётся, если с прошлого тега нет коммитов, влияющих на версию.

Коммит с `CHANGELOG.md` пушится прямо в `main`, а на ней включено правило «Require a pull request». Нужен один из вариантов:

1. Добавить в bypass list правила пользователя/приложение, под которым идёт пуш, и положить его токен в секрет `RELEASE_TOKEN` (fine-grained PAT с правом `Contents: write`).
2. Если bypass для `GITHUB_TOKEN` поддерживается правилом, секрет не нужен: workflow использует `RELEASE_TOKEN`, а при его отсутствии `GITHUB_TOKEN`.

Пока версия ниже `1.0.0`, правила те же: `bugfix` и `hotfix` дают `0.1.1`, `feature` — `0.2.0`, а `[!!]` сразу переводит проект на `1.0.0`.

Деплой релиз не запускает: CI слушает только `dev`. Перевод деплоя на теги — отдельная задача после демо.
