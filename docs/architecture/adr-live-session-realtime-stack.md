# ADR: стек реального времени для сессии интервью — LiveKit + CodeMirror/Yjs

## Статус

Принято.

## Контекст

Сессия интервью — это видео/аудио-звонок между интервьюером и кандидатом плюс общий редактор
кода, в котором оба видят правки и курсоры друг друга в реальном времени. Это два независимых
канала реального времени с разными требованиями (медиапотоки против синхронизации текстового
документа), но используются вместе и запускаются в рамках одной сессии.

До этого решения в таблице архитектурных решений видео было зафиксировано как Jitsi Meet
(embed), а реалтайм-редактор оставался открытым вопросом. Команда собрала изолированный PoC —
[`experiments/livekit-codemirror`](../../experiments/livekit-codemirror) - чтобы проверить
LiveKit и связку CodeMirror 6 + Yjs на практике в одном браузерном окне, не подключая их к
основному frontend-приложению.

## Рассмотренные варианты

### Видео/аудио: LiveKit (выбрано, заменяет Jitsi Meet)

PoC подтвердил, что LiveKit покрывает нужный сценарий: двусторонний видео/аудио-звонок с
токен-based доступом к комнате (participant token, выдаваемый сервером). В отличие от Jitsi
Meet (готовый embed-виджет со своим UI), LiveKit — SDK с собственным UI поверх собственного
UI, что даёт больше контроля над версткой звонка внутри страницы сессии, но требует backend
для выдачи токенов на комнату (в PoC для этого временно использовался LiveKit Cloud
Development Token Server — см. «Что осталось сделать перед продакшеном» ниже).

### Реалтайм-редактор: CodeMirror 6 + y-codemirror.next + Yjs + y-websocket (выбрано)

- **CodeMirror 6** — редактор кода.
- **Yjs** — CRDT, разрешающий конфликты одновременного редактирования без центрального
  ревизионного сервера.
- **y-codemirror.next** — официальный биндинг Yjs к CodeMirror 6 (синхронизация текста и
  курсоров участников).
- **y-websocket** — транспорт, передающий Yjs-обновления между браузерами через WebSocket.

PoC подтвердил одновременное редактирование без потери символов и отображение курсора
второго участника. Этот канал синхронизации независим от LiveKit: видео/аудио идёт через
LiveKit SFU, а изменения документа — через отдельный `y-websocket`-сервер.

## Решение

- Видео/аудио сессии интервью — **LiveKit**.
- Совместный редактор кода — **CodeMirror 6 + y-codemirror.next + Yjs + y-websocket**.

## Что осталось сделать перед продакшеном

PoC намеренно использует временные заглушки, зафиксированные в
[`experiments/livekit-codemirror/README.md`](../../experiments/livekit-codemirror/README.md):

- Публичный демонстрационный `wss://demos.yjs.dev/ws` нужно заменить собственным
  авторизованным `y-websocket`-провайдером.
- Имя Yjs-документа сейчас — константа (`interviewly-yjs-experiment`); нужно формировать его
  из ID сессии интервью.
- Состояние `Y.Doc` нигде не персистится — нужна привязка к БД (или хотя бы periodic snapshot).
- LiveKit Development Token Server (без backend-аутентификации) нужно заменить на реальный
  backend-эндпоинт выдачи participant token, привязанный к участнику и сессии.
- В интерфейсе ещё нет управления камерой/микрофоном (mute/unmute).
- Для доступа к камере/микрофону с другого устройства (не localhost) понадобится HTTPS —
  браузеры блокируют media-устройства на обычном LAN HTTP.

## Последствия

- Плюс: оба канала (видео и совместный редактор) проверены совместно в PoC — интеграционных
  сюрпризов при подключении к основному приложению ожидается меньше.
- Плюс: `y-websocket` и LiveKit независимы друг от друга — сбой/деградация одного канала не
  обязана ронять другой.
- Минус: два разных backend-компонента для реального времени (LiveKit-токен-эндпоинт и
  `y-websocket`-сервер с персистентностью `Y.Doc`) вместо одного — больше поверхности для
  эксплуатации и мониторинга, чем при единственном embed-решении вроде Jitsi Meet.
- Открытые пункты из PoC (см. выше) остаются в бэклоге до подключения стека к основному
  frontend-приложению.
