# ADR: URL-first интернационализация фронтенда

## Статус

Принято.

## Контекст

Интерфейс Interviewly изначально создаётся на русском языке, но должен поддерживать добавление
других языков без массового рефакторинга компонентов и маршрутов. Первые поддерживаемые языки —
русский и английский.

Локаль влияет не только на текст React-компонентов. От неё также зависят URL, серверный рендеринг,
metadata страницы, атрибут `lang` корневого HTML-элемента и внутренние ссылки. Серверные и
клиентские компоненты должны получать один и тот же язык при первом рендеринге, чтобы не возникало
расхождения при гидратации.

Переводимые строки должны находиться в одном типизированном словаре. Для каждого сообщения рядом
хранятся варианты на всех поддерживаемых языках. TypeScript проверяет полноту переводов и
допустимые ключи при сборке.

## Рассмотренные варианты

### 1. Хранить язык только в cookie

При таком подходе все языки используют одинаковые адреса (`/profile`, `/sessions`), а сервер
выбирает перевод по cookie пользователя.

Вариант прост, но URL перестаёт однозначно определять содержимое страницы. Ссылку нельзя надёжно
передать другому пользователю с выбранным языком, сложнее настраивать кэширование и SEO, а cookie
может расходиться с ожидаемым языком текущей страницы.

### 2. Хранить язык только в клиентском состоянии

Локаль можно держать в React Context, Redux или `localStorage` и менять без участия сервера.

Вариант отклонён: серверные компоненты и metadata не получают язык при первоначальном запросе,
появляется риск показа языка по умолчанию до гидратации, а прямые ссылки по-прежнему не содержат
информацию о языке.

### 3. Использовать локаль в URL и запоминать её в cookie (выбрано)

Локаль является первым динамическим сегментом маршрута:

```text
/ru
/en
/ru/profile
/en/profile
/ru/sessions
/en/sessions
```

URL — источник истины для текущей страницы. Cookie хранит последний выбранный язык и используется
только для перенаправления с адреса без locale. При открытии `/en/profile` английский язык имеет
приоритет независимо от ранее сохранённого cookie.

## Решение

Использовать вариант 3: URL-first локализацию на основе динамического сегмента Next.js App Router
`app/[locale]`.

Поддерживаемые языки и язык по умолчанию определяются в одном месте:

```ts
export const SUPPORTED_LOCALES = ["ru", "en"] as const;
export type Locale = (typeof SUPPORTED_LOCALES)[number];
export const DEFAULT_LOCALE: Locale = "ru";
```

Порядок определения языка:

```text
locale в URL → cookie для URL без locale → DEFAULT_LOCALE
```

Запрос к адресу без locale перенаправляется на локализованный маршрут. Например:

```text
/profile → /ru/profile
```

Если пользователь посещает локализованный адрес, locale из URL записывается в cookie как его
последний выбор.

### Словарь

Переводы хранятся в `apps/frontend/src/shared/i18n.ts`. Для одного смыслового ключа варианты всех
языков расположены рядом:

```ts
const messages = {
  navigation: {
    profile: {
      ru: "кабинет",
      en: "profile",
    },
  },
};
```

Каждая запись проверяется типом `Record<Locale, string>`. После добавления языка в
`SUPPORTED_LOCALES` TypeScript показывает все сообщения, для которых отсутствует новый перевод.

Словарь разделён на смысловые группы (`navigation`, `auth`, `profile`, `session` и другие), но не
на отдельные файлы по языкам. Компонент получает только ключи выбранной группы.

### Использование в компонентах

Клиентские компоненты получают переводчик через React Context:

```tsx
const t = useTranslations("navigation");

return <span>{t("profile")}</span>;
```

Серверные компоненты получают locale текущего запроса и переводчик через серверный helper:

```tsx
const t = await getServerTranslations("navigation");

return <span>{t("profile")}</span>;
```

Внутренние переходы используют `LocalizedLink`, который добавляет текущий язык к адресу:

```tsx
<LocalizedLink href="/profile">{t("profile")}</LocalizedLink>
```

Результат для русского интерфейса:

```text
/ru/profile
```

Переключение языка заменяет locale-сегмент текущего URL, сохраняя остальной путь, query-параметры
и hash:

```text
/ru/profile?tab=stats → /en/profile?tab=stats
```

### Регистр текста

Словарь хранит естественное написание текста и не содержит отдельные варианты ради визуального
регистра. `uppercase`, `lowercase` и другие требования макета задаются Tailwind-классами на месте
отображения:

```tsx
<Badge className="uppercase">{t("available")}</Badge>
```

Бренды и аббревиатуры (`Interviewly`, `GitHub`, `AI`, `ID`) сохраняют корректное написание в
исходных данных или словаре.

### Контроль через ESLint

Правило `react/jsx-no-literals` запрещает добавлять пользовательский текст непосредственно в JSX.
Дополнительный AST-селектор проверяет строковые значения атрибутов `alt`, `aria-label`,
`placeholder` и `title`. Технические значения `className`, `href`, `id`, программный код,
идентификаторы и имена пользователей не переводятся.

Подробное описание правил находится в
[`apps/frontend/ESLINT-RULES.md`](../../apps/frontend/ESLINT-RULES.md).

## Добавление нового языка

Чтобы добавить язык:

1. Добавить locale в `SUPPORTED_LOCALES`.
2. Добавить перевод этого языка в каждую запись словаря.
3. Проверить локализованные маршруты и переключение языка.
4. Запустить `typecheck`, `lint` и production build frontend.

Отдельно изменять структуру App Router, React Context, proxy или компоненты при этом не требуется.

## Последствия

- Плюс: язык страницы однозначно определяется её URL, поэтому локализованной ссылкой можно
  делиться.
- Плюс: серверные и клиентские компоненты используют одну locale и один типизированный словарь.
- Плюс: добавление нового языка приводит к ошибкам TypeScript во всех незаполненных переводах.
- Плюс: прямые строковые литералы в пользовательском интерфейсе контролируются ESLint.
- Минус: все внутренние ссылки должны создаваться через `LocalizedLink` или другой locale-aware
  helper.
- Минус: для каждой новой UI-строки необходимо сразу добавить значения всех поддерживаемых
  языков.
- Минус: cookie и URL нужно синхронизировать, при этом URL всегда должен оставаться источником
  истины.
